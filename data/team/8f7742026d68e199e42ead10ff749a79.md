# 0. 使用方式与决策边界

本文件是项目技术开发的**唯一基线版本**；旧版PDF如与本文件的表数量、分支名、目录或接口约定不一致，以本文件为准，并由D同步更新PDF/协作说明。它不是另一个功能创意清单，而是**开发时遇到冲突以此为准**的工作约定。请四人逐节审阅后，在Git仓库共同确认V1.1；后续修改通过提交记录和变更日志追踪，不要分别维护相互矛盾的版本。

**已经确定、不再反复讨论的事项：**

1.  项目名为 **WorldCup
    Journey**，定位为“2026世界杯数据探索与记忆平台”。
2.  核心体验是“选择球队 → 球队DNA → 晋级之路 → 关键比赛 → 球队PK →
    生成纪念卡”；其中球队DNA、晋级之路和球队PK共享真实赛事数据，不独立维护统计副本。
3.  数据范围：**2026年48支参赛球队与104场比赛的基础信息**；**精选5—8场**补充比赛事件、标签及故事。不存在“必须收集所有比赛的全部事件”的要求。
4.  用户互动只包含**无注册纪念卡**与**公开留言+管理员审核**；没有普通用户账号、永久收藏、积分排行榜及实时比分接口。
5.  使用 **Yii2 + PHP +
    MySQL**；保持四人既有职责，**每人独立完成至少一套Model、View、Controller代码**。
6.  按老师的课程作业要求保留：团队及个人展示与后台编辑、留言、前后台管理、\>10张有实际用途的数据表、动态图形、下载入口、Git与项目管理工具、要求的目录/SQL及完整交付文档。

**统一约定（推荐冻结）：** 使用官方 `yiisoft/yii2-app-basic` 的 Yii
**2.0 稳定版 Basic 模板**；一套 Yii2 应用、一个 MySQL
数据库；用户侧以服务端渲染页面为主，动态图表只在需要时调用 JSON；首批共
**15 张业务表**；路由、字段名和返回格式按本文执行。

**待四人做最终环境确认：**
PHP小版本、MySQL实际版本、服务器运行方式（本地Apache/Nginx或PHP内置服务）、开发者系统差异、最终使用的CSS/图表资源来源。这些不改变本文规定的目录、数据字段和接口。

## 2.2 架构分层与职责

``` text
浏览器（Yii2 View / ECharts / 纪念卡前端生成）
        ↓ HTTP GET / POST （需要时返回JSON）
Controller（参数校验、访问控制、响应类型、页面导航）
        ↓ 调用共享服务 / Model
Service（TeamStatsService、JourneyService、MatchQueryService）
        ↓
Model / ActiveRecord（表映射、字段校验、关联）
        ↓
MySQL（唯一真实来源；不存重复的球队统计结果）
```

- **Model**负责字段验证与关系；**Service**负责跨表业务统计和组合查询；**Controller**尽量薄，避免把全部SQL写入View。
- **View**不得直接连接数据库或写SQL；所有链接使用Yii2的`Url::to()`生成，防止部署子目录时路径失效。
- 同一个统计量只有一个统一口径；B/C开发共享服务，A/D调用，避免自己重复计算。
- 第一版不单独部署前后端、不引入微服务、不设计复杂REST认证。

# 3. 数据库模型：15张表的统一基线

## 3.1 公共数据库规范

- 数据库建议命名：`worldcup_journey`，字符集`utf8mb4`，排序规则统一选用MySQL
  8可用的`utf8mb4_0900_ai_ci`（如因版本不同调整，须全组同步）。
- 主键一律使用`id BIGINT UNSIGNED AUTO_INCREMENT`；外键对应同类型；命名`*_id`。**例外：多对多关联表可采用联合主键**。
- 表名、字段名、文件名用英文小写下划线；代码类名用PascalCase；参数和JSON键使用snake_case。**不能把名称或球队中文文本当作关联主键**。
- 每张主表建议有`created_at DATETIME`、`updated_at DATETIME`；只读字典表可适当省略，需在数据字典里注明。
- 时间统一：`kickoff_utc`为UTC，数据库列为DATETIME（不自动带时区），应用导入、查询和展示时必须转换；其它`*_at`字段也按UTC存储。
- 重要关联使用真实外键；删除使用`RESTRICT`或必要的**受控软删除**，禁止级联清空真实比赛历史。关联表如`match_story_tag`可以`ON DELETE CASCADE`。
- 每个字段需有明确的空值语义。球队/比赛的统计指标由聚合计算，**不另设冗余的进球总数、胜率统计表**。
- 业务状态使用统一代码字符串；后端常量与文档同步，页面再翻译为中文。

`final_result_code`建议值：`GROUP`（小组出局）、`R32`、`R16`、`QF`、`FOURTH`、`THIRD`、`RUNNER_UP`、`CHAMPION`。它表示**最终成绩类别**，不代表国际足联对48队进行的逐名次排序；若来源没有明确结论先保留空值。

| 字段                               | 类型              | 约束/含义                                                                                                                          |
|------------------------------------|-------------------|------------------------------------------------------------------------------------------------------------------------------------|
| `id`                               | BIGINT UNSIGNED   | PK                                                                                                                                 |

| `match_no`                         | SMALLINT UNSIGNED | NN；与tournament_id组合唯一，1–104                                                                                                 |
| `home_team_id`, `away_team_id`     | BIGINT UNSIGNED   | FK NN → national_team；两者不得相同                                                                                                |
| `stadium_id`                       | BIGINT UNSIGNED   | FK NN → stadium                                                                                                                    |

| `status`                           | VARCHAR(16)       | NN，默认`SCHEDULED`；`SCHEDULED`/`IN_PROGRESS`/`FINISHED`/`POSTPONED`/`CANCELLED`；不接入实时比分API，状态由后台维护或导入数据提供 |
| `home_score_90`, `away_score_90`   | TINYINT UNSIGNED  | 比赛结束后必须成对填写；**90分钟（含补时）比分**；未结束时可空                                                                     |
| `home_score_120`, `away_score_120` | TINYINT UNSIGNED  | 可空且必须成对填写；**含加时赛最终比分**，只有踢了加时时填写；不得只存加时赛新增进球                                               |
| `home_penalties`, `away_penalties` | TINYINT UNSIGNED  | 可空且必须成对填写；仅有点球决胜时填写，不并入场上比分                                                                             |
| `winner_team_id`                   | BIGINT UNSIGNED   | FK可空；淘汰赛胜出方（含点球获胜、第三名赛和决赛）；平局无胜方时为空                                                               |
| `summary`                          | VARCHAR(300)      | 可空；比赛一句话摘要（不等同故事正文）                                                                                             |

**必须统一的比分规则：** 展示最终场上比分 =
若`*_score_120`有值则用120分钟比分，否则用90分钟比分；**点球命中数绝不加进球队总进球**。有点球大战时显示如“1–1（点球4–3）”。`winner_team_id`只记录淘汰赛、季军赛或决赛的最终晋级/获胜方，必须是本场双方之一；小组赛不填写。它**不能直接用于计算‘场上获胜场次’**。所有数据以同一球队ID为准，主客队位置不影响统计。项目语义上的“主队/客队”仅指比分展示顺序，不推定真实主场优势。

**状态与比分约束：**
`FINISHED`比赛必须填写成对的`home_score_90/away_score_90`；`home_score_120/away_score_120`必须同时为空或同时有值，且填写时表示累计至加时结束的总比分，不能小于对应的90分钟比分；点球比分必须成对填写，并且只用于点球决胜展示。点球比分存在时，`winner_team_id`必须与点球较高的一方一致。已结束的淘汰赛、季军赛和决赛必须有`winner_team_id`；小组赛不填写。`SCHEDULED`、`POSTPONED`、`CANCELLED`比赛不得伪造赛果；`IN_PROGRESS`仅表示人工维护的比赛状态，不代表系统提供实时比分。以上约束由Model/Service校验，并在数据库层尽可能增加CHECK约束。

`wc_match`索引至少包括：`UNIQUE(tournament_id,match_no)`、`INDEX(tournament_id,kickoff_utc)`、`INDEX(home_team_id)`、`INDEX(away_team_id)`、`INDEX(stage_code)`；外键的关联球队需验证属于同一赛事（导入脚本/业务层检查）。

### B. 精选比赛（仅5—8场录入完整内容）

**`match_event`（B）**：`id BIGINT PK`、`match_id BIGINT FK NN`、`team_id BIGINT FK NULL`、`player_name VARCHAR(100) NULL`、`minute SMALLINT UNSIGNED NULL`、`added_minute SMALLINT UNSIGNED NULL`、`period_code VARCHAR(12) NN`、`event_type VARCHAR(20) NN`、`description VARCHAR(500) NULL`、`sort_order INT NN DEFAULT 0`。建议`period_code`取`H1/H2/ET1/ET2/SHOOTOUT`；`event_type`取`GOAL/OWN_GOAL/YELLOW/RED/PENALTY_GOAL/PENALTY_MISS/OTHER`。`minute`记录比赛计时显示的基础分钟数（如45、67、105），`added_minute`记录补时分钟数，例如45+2存为`minute=45`、`added_minute=2`；点球大战事件使用`period_code=SHOOTOUT`，此时分钟字段可空。`PENALTY_GOAL/PENALTY_MISS`表示点球相关事件，具体属于常规比赛点球还是点球大战由`period_code`区分。`sort_order`用于同一分钟内稳定排序。事件用于展示时间轴，**不作为球队进球统计的计算来源**；进球统计只读取`wc_match`比分字段。建议增加`INDEX(match_id, sort_order)`。

**`match_story`（B）**：`id BIGINT PK`、`match_id BIGINT FK NN UQ`、`title VARCHAR(150) NN`、`summary VARCHAR(500) NN`、`body TEXT NN`、`cover_path VARCHAR(255) NULL`、`source_url VARCHAR(600) NULL`、`is_published TINYINT(1) NN DEFAULT 0`、`created_at/updated_at`。只有审核过事实与素材使用许可的内容可发布；`is_published=0`时，前台只展示该场比赛基础详情，不展示对应故事正文、事件时间轴和标签；发布后再一并展示精选内容。

**`match_tag`（B）**：`id BIGINT PK`、`code VARCHAR(40) NN UQ`、`name VARCHAR(40) NN`；如`PENALTY_SHOOTOUT`、`COMEBACK`、`HIGH_SCORING`、`KNOCKOUT`。**`match_story_tag`（B）**：`story_id BIGINT FK`、`tag_id BIGINT FK`，复合PK。故事删除时允许清理对应标签关联，但不得级联删除比赛实体。

### C. 课程团队、作业、留言、管理员

**`project_team`（A）**：`id PK`、`name VARCHAR(100) NN`、`description TEXT`、`logo_path VARCHAR(255) NULL`、`updated_at`。当前只有一个课程团队，仍用表维护。

**`project_member`（A）**：`id PK`、`project_team_id FK NN`、`display_name VARCHAR(80) NN`、`role_title VARCHAR(100) NN`、`bio TEXT NULL`、`sort_order INT NN DEFAULT 0`、`updated_at`。按课程要求展示四位成员及实际工作分工。

**`project_document`（A）**：`id PK`、`project_team_id FK NN`、`member_id FK NULL`、`document_type VARCHAR(10) NN`（`TEAM`/`PERSONAL`）、`title VARCHAR(160) NN`、`relative_path VARCHAR(255) NN`、`original_name VARCHAR(255) NN`、`file_size BIGINT UNSIGNED`、`uploaded_at DATETIME`。约束：`PERSONAL`必须绑定`member_id`；`TEAM`不绑定成员；文件只能存放并下载自受控的`data/team`或`data/personal`路径。

**`admin_user`（D）**：`id PK`、`username VARCHAR(60) NN UQ`、`password_hash VARCHAR(255) NN`、`auth_key VARCHAR(100) NN`、`status TINYINT(1) NN DEFAULT 1`、`last_login_at DATETIME NULL`、`created_at/updated_at`。**不存明文密码**；由Yii2的PasswordHelper进行哈希验证；不能提交预设弱口令。

**`guestbook_message`（D）**：`id PK`、`nickname VARCHAR(50) NN`、`content TEXT NN`、`related_match_id BIGINT FK NULL`（从精选比赛进入时可关联比赛，否则为普通留言）、`status VARCHAR(12) NN DEFAULT 'PENDING'`（`PENDING/APPROVED/REJECTED`）、`created_at/updated_at`。必须控制内容长度，严格过滤输出，禁止直接渲染HTML。

**`guestbook_reply`（D）**：`id PK`、`message_id BIGINT FK NN UQ`、`admin_user_id BIGINT FK NN`、`content TEXT NN`、`created_at/updated_at`。首版**一条留言最多一条管理员回复**，审核通过后再公开显示回复；多轮对话不是本次范围。

## 3.5 数据导入及完整性验证

**分工与来源：**
C统一导入程序和ID映射，负责48队与参赛分组；B负责104场基础数据、场馆、精选比赛内容；A只提供可合法使用的队徽/图片路径；D执行一次独立复核。B向C提交赛事源数据文件时，球队优先使用`fifa_code`、场馆使用可核验的官方名称作为映射键，**不要在源CSV中自行编造数据库自增ID**；C在导入时统一解析为`national_team.id`、`stadium.id`等内部ID。建议在`data/import/`存放结构化CSV/JSON，在`docs/data-sources.md`记录来源、整理日期、字段映射和复核人。数据优先与FIFA官方赛程结果核对，Excel/CSV只是导入中间格式，不作为网站运行时数据源。

**建议导入顺序：** `tournament` → `national_team` → `stadium` →
`tournament_team` → `wc_match` →
`match_story`/`match_event`/`match_tag`/`match_story_tag` →
项目团队/管理员/留言测试数据。

**导入检查项：**

- 2026赛事1条、48支球队、48条该届参赛关系、104场比赛；分组12组每组4队。
- 104场分为72场小组赛和32场淘汰赛（16+8+4+2+1+1）；每场双方不同、球员/球队ID有效、比赛编号不重复。

# 4. 统一统计口径（球队DNA / PK / 图表）

## 4.1 不允许各页面各算一遍

所有分析都以**2026年`wc_match`表中`status='FINISHED'`的数据**为事实源，通过`TeamStatsService`返回标准字段；首页图表与纪念卡同样复用服务。

设球队T的比赛集合为：`wc_match`中`home_team_id=T`或`away_team_id=T`的**已结束比赛**。对于每场比赛，先按T在主/客队位置读取其比分，再计算下列指标。

| 指标/返回字段             | 规则                           | 显示注意                                      |
|---------------------------|--------------------------------|-----------------------------------------------|
| `matches_played`          | 已结束比赛场数                 | 小组赛和淘汰赛全部计入                        |
| `goals_for`               | 该队每场最终场上进球求和       | 加时比分计入；点球决胜射入球不计入            |
| `goals_against`           | 对方每场最终场上进球求和       | 同上                                          |
| `wins`                    | 最终场上比分领先的比赛数       | 点球淘汰对方但场上打平不算W                   |
| `draws`                   | 最终场上比分相等的比赛数       | 包括最终进入点球大战的平局                    |
| `losses`                  | 最终场上比分落后的比赛数       | `W+D+L=比赛场数`                              |
| `goals_per_match`         | `goals_for/matches_played`     | 分母为0时返回null，不返回除零异常             |
| `goals_against_per_match` | `goals_against/matches_played` | 保留两位小数，只在展示层四舍五入              |
| `win_rate`                | `wins/matches_played`          | 0–1的小数；前端按百分比展示                   |
| `penalty_wins`            | 在点球决胜中获胜的场次         | 独立指标，避免误当场上胜场                    |
| `final_result_code`       | 来自`tournament_team`          | 显示“最终成绩类别/止步阶段”，不随意称官方名次 |

**细节：**
SQL中应显式处理主/客队转换与`COALESCE(score_120,score_90)`；当一场淘汰赛90分钟1:1、120分钟仍1:1、点球4:3时，计为一场平局，进失球各1，点球胜出一方`penalty_wins`+1。

**雷达图不作为首版必需**：如确实要做，必须给每个维度同样的归一化区间，标注“数值越大是否更好”，特别是失球指标要反向变换；第一版建议**数值卡+分组柱状图/对比表**，更准确也更容易测试。

## 4.2 球队PK、晋级之路与报告

- `TeamStatsService->getTeamStats(int $teamId): array`一套逻辑供DNA、PK、首页、纪念卡调用；PK同时调用两支球队的统计结果，不存新的PK分数。
- `JourneyService->getTeamJourney(int $teamId): array`按`kickoff_utc`再按`match_no`排序，返回对手信息、阶段、场上比分、点球、晋级信息和`wc_match.id`；该方法名在全文统一使用，不再使用`getJourney()`这一旧称。
- 经典比赛详情在基础比赛之上可选关联`match_story`、`match_event`、`match_tag`和`match_story_tag`；没有故事的比赛仍应正常显示。
- 如将来加入球队分析报告导出，直接复用标准统计结果和旅程接口；**不作为V1.1开发承诺**。

## 4.3 预定的三类动态图表

| 图表                                | 数据源/查询                                           | 主负责人                               | 验收                                                         |
|-------------------------------------|-------------------------------------------------------|----------------------------------------|--------------------------------------------------------------|

上述为**统一接口契约/建议的方法签名**；并非声称目前已经有这些实现。统一采用**服务实例方法**，通过Yii2依赖注入或显式创建实例使用；签名、字段、类型和异常语义一旦冻结不能私自修改。`ApiController`由B维护路由与响应封装，球队统计的实际计算仍由C的`TeamStatsService`负责；C不直接修改B的API控制器文件，如需调整返回字段先更新接口契约并通过PR协商。

**`getTeamStats()`返回字段样例（仅结构，数字为示意而非真实赛果）：**

``` json
{
  "team_id": 12,
  "team_name": "示例球队",
  "fifa_code": "XXX",
  "matches_played": 5,
  "wins": 3,
  "draws": 1,
  "losses": 1,
  "goals_for": 9,
  "goals_against": 5,
  "goals_per_match": 1.8,
  "goals_against_per_match": 1.0,
  "win_rate": 0.6,
  "penalty_wins": 0,
  "final_result_code": "R16"
}
```

**`getStageSummary()`返回结构（字段约定）：**

``` json
[
  {
    "stage_code": "GROUP",
    "match_count": 72,
    "finished_match_count": 0,
    "total_goals": null
  }
]
```

- `match_count`：该阶段有效比赛记录数，不计`CANCELLED`；包括尚未开始、进行中、已结束和延期比赛。
- `finished_match_count`：`status='FINISHED'`的比赛数。
- `total_goals`：只汇总已结束比赛的场上总进球；分别使用`COALESCE(home_score_120, home_score_90)`与`COALESCE(away_score_120, away_score_90)`后相加，不计点球大战进球。该阶段尚无已结束比赛时返回`null`，不得用0冒充已核实的进球总数。
- 上例中的`finished_match_count=0`和`total_goals=null`仅用于展示“该阶段尚无完赛数据”的结构；正式数据必须由数据库查询生成。

**`getTeamJourney()`单条数据示例（同样仅示意）：**
方法返回该球队本届赛事的全部比赛记录，按开球时间排序；`goals_for/goals_against`使用最终场上比分（优先120分钟比分），未完赛时为`null`；点球比分单独放入`penalties_for/penalties_against`。淘汰赛的`advancement_result`可取`ADVANCED/ELIMINATED`，小组赛为`null`。

``` json
{
  "match_id": 20,
  "match_no": 20,
  "kickoff_utc": "2026-06-18T19:00:00Z",
  "stage_code": "GROUP",
  "opponent": {"team_id": 25, "name_zh": "示例对手"},
  "is_home": true,
  "goals_for": 2,
  "goals_against": 1,
  "penalties_for": null,
  "penalties_against": null,
  "advancement_result": null,
  "is_featured": false
}
```

**输入异常约定：**
不存在的球队/比赛ID抛`NotFoundHttpException`或返回明确的查无结果；数据缺失的统计值使用`null`并显示“暂无”，不得默认为零来误导；MySQL错误写服务端日志、用户只看到友好信息。

## 5.3 JSON接口约定（用于异步图表/局部数据调用）

提供三个只读JSON入口：`api/team-stats?id=...`、`api/team-compare?left_id=...&right_id=...`、`api/insights?chart=stage-goals`。三个入口统一由B维护的`ApiController`接收请求；前两个调用C的`TeamStatsService`，第三个调用B的`MatchQueryService`。所有成功响应统一格式：

``` json
{
  "success": true,
  "data": {"team_id": 12, "matches_played": 5},
  "error": null
}
```

失败时HTTP状态码正确设置为400/404/403/500，返回：

``` json
{
  "success": false,
  "data": null,
  "error": {"code": "TEAM_NOT_FOUND", "message": "未找到该球队"}
}
```

常用错误码建议：`INVALID_PARAMETER`（参数格式错误）、`TEAM_NOT_FOUND`（球队不存在）、`MATCH_NOT_FOUND`（比赛不存在）、`INVALID_CHART`（不支持的图表类型）、`FORBIDDEN`（无权限）。错误信息面向用户，不返回SQL、服务器路径或敏感配置。

`ApiController`对应`api/team-stats`、`api/team-compare`、`api/insights`三个GET只读入口，相关动作应返回`Response::FORMAT_JSON`，JSON键用snake_case，文本UTF-8。`api/team-stats`和`api/team-compare`只负责参数校验及调用C的`TeamStatsService`；`api/insights?chart=stage-goals`调用B的`MatchQueryService->getStageSummary()`。按Yii2默认路由，三个入口分别对应`ApiController::actionTeamStats()`、`ApiController::actionTeamCompare()`和`ApiController::actionInsights()`。这些接口不提供写入/删除能力。**不要为了“有接口”把所有普通页面都改成JSON；页面View仍由其负责人的Controller渲染。**

# 7. 编码、Git、安全与质量规范

## 7.1 PHP与前端编码要求

- 控制器类PascalCase，如`NationalTeamController`；模型与服务相同；方法camelCase，如`getTeamStats`；SQL表与字段、JSON键snake_case；资源文件kebab-case。
- 每个本组新增PHP文件都包含统一注释头：用途、负责成员、所属模块、重要依赖、修改日期；**不要在注释头写真实个人隐私或账号密钥**。
- 业务校验优先放Model表单规则/Service；数据库保持约束；模板输出用户文本必须经Yii2
  HTML编码，禁止直接echo未经处理的留言或故事正文。
- 不得用字符串拼接SQL参数；使用ActiveRecord、Query Builder或绑定参数。
- 前端统一公共导航、字体和按钮样式；A维护`AppAsset`，其他人不得直接在不同页面重复引用不同版本的ECharts/jQuery。
- 上传限制类型、大小与存储目录；使用服务端生成文件名/相对路径，不信任浏览器原始路径；下载通过数据库ID映射合法目录并检查路径，防止目录穿越。

- 每张任务卡对应该功能说明、负责人、预计完成日期、验收方式、PR链接；状态建议`待做/进行中/待联调/已完成`。
- 每次提交只处理一个相对完整的变更；提交信息例如`feat(team): add stats service`、`fix(match): handle penalty result`、`docs(api): freeze journey contract`。
- PR统一以`develop`为目标分支（发布/阶段验收时另行确认是否合入`main`）；最低要求：改动说明、影响文件、接口/数据库变更、运行与测试结果、页面截图（适用时）。至少由**另一位组员**复核后合并；涉及跨模块接口应通知调用方。
- **数据库schema变更必须先修改数据字典，再修改`install.sql`或迁移文件**；本组只维护一份最终有效的`install.sql`，由C合并各成员已确认的表结构和演示数据。各成员可在自己的本地数据库验证，但不要各人私自修改共享仓库之外的“最终结构”或覆盖他人的表定义。
- 合并冲突由文件负责人和改动人共同解决；合并后D执行基础冒烟测试。禁止使用覆盖目录/发送压缩包作为主要协作方式。

## 7.3 安全最低要求

| 风险                   | 必须采用的措施                                                        |
|------------------------|-----------------------------------------------------------------------|
| 未授权后台操作         | 所有后台Controller使用AccessControl，登录判定由Yii2组件统一负责       |
| HTTP方法滥用           | 删除/审核/修改等操作只允许POST；Yii2 CSRF开启；GET只查询与下载        |
| SQL注入                | ActiveRecord/参数化查询；对排序字段使用白名单                         |
| XSS                    | 留言和用户感想HTML编码；富文本故事如用HTML须白名单净化                |
| 密码泄露               | 哈希存储；配置不提交；初始管理员通过本地安全命令/脚本创建             |
| 目录穿越和任意文件读取 | 下载只接受合法记录ID，路径受控`data/team`或`data/personal`，阻止`../` |
| 文件上传               | 类型/尺寸白名单、随机存储名、禁止PHP/脚本扩展、Web根之外存储          |
| 垃圾留言               | 内容长度限制、简单提交频率限制、默认待审核                            |
| 调试信息泄露           | 演示部署关闭debug/Gii；异常不返回数据库密码或内部路径                 |

管理员登录只需要一类管理员角色，不必做多角色RBAC。纪念卡的感想文本可只在当前浏览器生成，不保存到服务器；公开留言必须入库并经过审核。
